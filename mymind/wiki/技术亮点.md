# mymind 技术亮点

适用范围：Python 主版本，2026-10-07。本文说明已有实现和设计取舍，实验结果与运行时能力分别表述。

## 1. 请求从意图判断走到工具执行

系统先用意图识别组织业务领域，再由 Agent 结合上下文选择工具。意图负责路由；是否查知识库由模型发起 `search_knowledge_base` 调用决定。

![请求执行顺序](assets/flows/01-chat-flow.png)

请求级 `Request` 贯穿背景、实体、路由和工具执行，完整 UUID 将聊天响应与 Trace 关联。默认启用工具调用与工具式 RAG；Profile、独立人工升级、Composer 与 Trace 保持可配置且默认关闭。

## 2. 三路意图融合先选领域，再选细意图

LLM 处理上下文语义，模板 Embedding 匹配常见表达，Pattern 提供低开销业务线索。正常权重为 `0.7/0.2/0.1`，Embedding 禁用时为 `0.85/0.15`。

粗意图和细意图分别计分会拆散同领域证据。当前 `_vote()` 同时保存具体意图分与领域分，先决定领域，再在领域内选择意图。例如技术粗分 `0.04` 加登录故障 `0.18` 的合计 `0.22` 可以胜过账单 `0.21`，而不是仅比较最大单项。

Pattern 细化限定为胜出的同一领域，保留置信度至少 `0.5`、领域分低于 `0.8` 等原条件。LLM 失败走 Embedding/Pattern 的独立兜底，不把失败结果伪装成正常融合结果。

`source_scores` 保留原始置信度；最终置信度来自融合或细化。识别结果按当前消息与有限历史缓存，避免重复识别仍然耗用模型调用。

## 3. 主辅路由表达复合业务问题

领域分由意图、关键词、错误码、金额和订单号实体共同构成。最高分领域负责主问题，达到阈值或具有明确协作信号的专业领域作为辅助。

例如登录故障同时出现重复扣款，技术与账单都可以执行；主辅次序由领域分确定。辅助领域不能只因主领域得分高就被过滤，也不能绕过监控的可用性筛选。

`RoutingDecision` 保存主领域、辅助列表、理由和置信度。`primary_agent` 描述决策，`agent_type` 与 `agent_types` 说明执行结果。专业执行失败后回退 GeneralAgent，保留已经发生的工具轨迹。

Composer 开启时承担回复合成；默认配置采用带角色标签的拼接。这样可以分别评估领域协作是否正确和合成是否带来质量收益。

## 4. 工具状态属于单次请求

共享 Agent 可以同时处理多个请求。把“最后一次工具”写在实例上会使并发请求互相覆盖；当前工具循环只用局部变量，最终以 `AgentCallResult` 返回内容、状态、工具名称、轨迹和聚合用量。

正常结束、模型续轮失败、GeneralAgent 回退都保留已有工具记录。并发回归使用同一技术 Agent 处理 401 和 500 两个请求，核对输入、调用 ID 和持久化 Trace 的隔离。

工具执行前检查角色白名单和 Schema。越权和非法参数形成失败轨迹，不执行处理函数；实际进入处理的工具会记录到 `tools_used`。轨迹输入做现有脱敏，不保存完整工具结果正文。

## 5. 多 Provider 网关统一工具协议与用量

`LLMRequest/LLMResult/ToolCall/CacheUsage` 把 Anthropic、OpenAI、DeepSeek 原生及 Anthropic 兼容端点的差异收束在网关层。业务 Agent 不必分别解析每个 SDK 的响应。

网关保留可续轮的 assistant 消息，再以 Provider 协议回送工具结果。明确不支持工具协议时可降级为无工具生成，并在轨迹记录原因。工具续轮用量聚合后进入缓存指标，输入、输出与缓存命中 Token 分开统计。

应用缓存、Provider Prompt Cache 与请求工具缓存是不同层次。前者避免重做业务结果；Provider 缓存影响上游处理成本；请求工具缓存只复用当次已完成的相同查询。指标显示命中不等于已经证明总体成本收益。

## 6. RAG 触发与检索优化分开

![RAG 工具链](assets/flows/04-rag-tool-flow.png)

Agent 决定是否检索，MCPToolManager 负责检索过程：查询改写、原查询保留、并行召回、结果缓存、熔断、超时、去重和重排。

改写失败回到原查询；降级片段被排除在正常知识合并结果之外；重排失败用确定性排序。`reranked=true` 表示经过管理器重排阶段，片段数已经不足 Top-K 时可能没有实际模型调用。

生产 KnowledgeBase 默认为向量检索和句子切块。Markdown 感知 `500+80` 切块、BM25+RRF 与不同索引版本在 R0–R4 实验中对照，不能把实验配置描述成默认生产行为。

聊天的 `knowledge_used` 表示已进入检索工具处理，`knowledge_status` 另行区分片段、空结果、降级和失败。检索命中也不能单独证明模型最终回答有可靠依据，需要结合回答内容和质量评测。

## 7. 知识库导入保持幂等

稳定片段 ID 配合 Chroma `upsert`，重复导入相同文档不增加副本；正文随写入参与向量生成。导入成功后使知识结果缓存失效，避免继续返回旧检索缓存。

`processed_chunks` 是本次提交的处理量；旧字段 `added_chunks` 保留兼容含义。它不等于 collection 的净增长。正文或结构变更可能产生新 ID，旧片段不会因 upsert 自动删除。

## 8. 记忆控制长期对话的背景规模

Redis 存当前会话消息与摘要；Chroma 存用户情景记忆与画像。15 条消息触发压缩，保留最近 5 条，并将旧消息摘要写入情景记忆。消息数与轮次数区分明确。

会话写入和压缩持有 Redis 会话锁，防止慢摘要覆盖新消息；画像更新按用户加锁，并在没有新用户内容或 600 秒更新间隔内跳过模型调用。异步 Chroma 访问通过线程卸载，避免同步向量库请求阻塞事件循环。

ContextBuilder 在默认 8000 字符背景预算内逐步减少低优先级记忆，同时把当前问题作为独立输入保留。该预算不涵盖后续所有工具结果，也不是整个请求的 Token 限制。

## 9. Skills 与角色代码分工

角色代码处理路由、工具和状态；Skill 文档提供业务话术、排查顺序和必需信息。Skill 按角色与关键词匹配，独立限制 Prompt 长度，`/skills/reload` 热加载。

文件解析失败单独报告，不影响其他 Skill。修改 Skill 需要检查 `/skills` 和实际命中日志；Skill 是模型输入规范，不是对模型输出的确定性约束。

## 10. 监控反馈在单实例中也能改变路由

Monitor 用在线成功率和耗时计算 `monitor_penalty`，每 10 秒采样回写。只把惩罚值放进实例排序时，单实例类型仍然会被选中；当前路由额外检查专业类型是否全部实例达到默认 `0.5` 阈值。

全部高降权时剔除类型，有健康实例时仅选择健康实例；辅助协作也使用同一候选集合。`monitor_fallback=[...]` 说明本次路由真正发生了类型过滤。统计告警与类型过滤属于不同条件。

## 11. 验证分层与项目展示

| 验证层 | 可以说明什么 |
| --- | --- |
| 假模型单元与 API 契约 | 数据字段、成功/失败分支、并发隔离与接口兼容。 |
| E0–E5 确定性 Agent 实验 | 固定数据上路由、工具选择与策略连接是否符合预期。 |
| R0–R4 检索与真实 Chroma 层 | 特定语料、Embedding、切块和代理策略下的检索表现。 |
| 付费真实模型与 Judge | 指定模型、数据和运行预算下的质量、Token 与延迟。 |

2026-10-07 回归 83 项通过，包含 E0–E5 离线门禁；Compose 和 HTTP 契约检查通过。历史真实 DeepSeek E0/E5 的质量、Judge 完整性和 Token 成本门禁未通过，不能用离线通过覆盖该结论。

项目展示可说明“意图领域融合、主辅编排、Agent 工具式 RAG、三级记忆、可配置监控回退与分层评测已经落地”。退款、账户修改和真实工单仍是后续业务系统接入边界，不能用生成话术代替实际操作。
