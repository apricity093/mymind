## 四 阶段一 修复工程问题

### 一 明确检索总预算和 Google 子预算

现状：Google HTTP 请求超时为 30 秒，工具总超时也为 30 秒。Google 超时后才开始备用检索，结果可能已经无法交给调用者。首次调用还可能先执行元数据与 token 计数请求。

实施要求：

- 保留工具总预算 30 秒作为起点；Google 查询阶段建议总预算 8 秒，包含该查询需要的等待、能力探测、计数和编码，而非每个 HTTP 请求都可再用 8 秒。
- 至少为备用检索和结果组装保留 10 秒。剩余时间用于调度和已有其他工作。该分配是本轮工程起点，不代表真实网络延迟保证；真实 smoke 后可以在不突破工具预算的前提下修正并记录。
- 文档导入、索引补齐、模板准备采用独立预算，不能把在线查询的 8 秒直接套到整批文档。
- 超时后应退出主查询阶段并执行预建的 MiniLM + BM25。备用失败时返回明确故障；不能把“暂不可用”的提示包装成检索成功证据。
- 仅在外层使用 `wait_for(to_thread(...))` 不足以取消同步 HTTP 或释放锁。处理实际请求的截止时间、线程生命周期和资源释放，确保超时后的后台工作不长期占锁、不继续写入旧结果缓存。
- Google 查询失败且主库完整时，后续正常查询可以恢复主路径。主库有待补齐内容时仍按原约定保持备用。
- 日志记录操作、原因、主备路径和是否返回真实证据，不记录密钥及完整业务正文。

验收用例必须经过 `MCPToolManager.call → knowledge_search → KnowledgeBase.search`，至少再覆盖一次 Agent 实际使用的检索工具路径：

| 场景 | 预期结果 |
|---|---|
| Google 立即失败 | 返回匹配问题的备用正文，`index_route=backup`，降级可观测 |
| Google 读取超时 | 在工具总预算前返回备用正文，工具没有提前用故障提示替代正文 |
| 计数慢且编码也慢 | 两阶段共用 Google 查询总预算，不按单个请求重新计时 |
| Google 恢复且主库完整 | 下一次正常请求使用主索引，失败结果不遮蔽恢复 |
| 主库未补齐 | Google 能正常编码查询也不能提前切回不完整主库 |
| Google 和备用均失败 | 明确失败并记录原因，不声称有知识证据 |

确定性测试可以缩短预算，例如工具 1 秒、主查询 0.2 秒、备用 0.05 秒，并用受控传输或同步事件触发超时。应验证返回备用正文及未触发工具外层超时，不依赖毫秒级相等断言。另以真实 MiniLM 执行一次延迟故障注入 smoke；故障标记为注入，不能写成真实 Google 故障。

### 二 消除事件循环阻塞并缩小锁范围

现状：异步 `/monitor` 间接同步执行 `KnowledgeBase.stats()`；导入、补齐和查询持有同一把锁等待 Google。监控请求会同步等待该锁，阻塞事件循环。`/knowledge/stats` 存在同类调用。

实施要求：

- 从异步端点调用的同步统计、存储或模型工作放入线程，或改用现有适合的异步接口。不得在事件循环线程同步等待知识库锁。
- 把远程编码移出保护索引可见状态的长时间锁。可以保留写入串行化，准备数据后在短提交阶段更新状态；不要为追求并行破坏一致性。
- 允许在途查询读取一个完整的提交前状态；要求更新接口成功返回后新发起的查询读取新状态。旧查询不能在更新后回填过期缓存。
- 缩小锁后必须验证更新、删除、补齐与查询之间的交互，不能只验证吞吐变快。
- 多个改写子查询的 Google 编码不应仅因同一个全局知识库锁而被串行化。确有本地组件线程约束时只串行对应小范围操作。

验收条件：

1. 用同步事件让一次导入或查询停留在模拟 Google 阶段。此时并发请求 `/monitor`、`/knowledge/stats` 和健康接口。健康请求应在释放 Google 阻塞前完成，事件循环心跳持续推进。
2. 统计接口可返回已提交快照；如果选择等待完整统计，它也只能异步等待，不能阻塞其他请求。对于已提交快照的实现，测试要求统计本身也在释放远程阻塞前返回。
3. 三个改写查询用受控事件证明至少两个进入编码阶段后才放行结果，不用真实 Google 做并发压力测试。
4. 更新、删除、补齐后，新查询不返回旧来源内容；旧在途查询不回填旧缓存；无跨模型向量查询。
5. 在固定本机、预热本地组件后补充 20 次轻量观测，记录健康接口 P50/P95 和事件循环最大停顿。以同步事件测试作为硬性正确性证据，不因一次系统调度抖动制造失败。

### 三 导入响应使用请求自己的结果

把 `/knowledge/add` 和 `/knowledge/upload` 改为保存 `import_documents()` 的返回字典，并用这个字典生成当前响应。避免经过其他 `await` 后再读共享 `last_import`。若旧调用者仍需 `add_documents()` 的计数返回，可保留已有入口；不额外建兼容框架。

验收：受控并发启动 A、B 两批导入，一批主索引成功，一批 Google 失败但备用成功；在 A 生成响应前允许 B 完成。两个响应的文档 ID、状态、`processed_chunks` 和提示必须分别对应自己的批次。两个端点都覆盖。`total_chunks` 可代表读取时全库总量，无需强制它等于单次导入完成时的瞬时值。

### 四 BM25 实验不执行 embedding

修正实验中无条件生成文档向量、读取向量缓存的路径。`mode=bm25` 只需要分块与词项索引，不调用文档或查询 embedding，不加载无关模型来构造向量。

公平比较仍需相同分块。如果 Gemini 分块需要远端计数，优先读取此前明确保存的分块；重新计数时单独记录 token 计数请求。这里的验收目标是“零 embedding 请求”，不能把它夸大为“必定零 Google HTTP 请求”。主生产路径依旧采用用户确定的混合检索。

验收：用一调用就抛错的 embedding stub 单独运行 BM25，仍能生成召回和指标；文档与查询 embedding 次数均为 0。使用已保存的同一分块时，Google 全部接口均不可用也应完成 BM25 实验。

## 五 阶段二 数据和评测契约

### 一 RAG 数据集

目标规模为约 50–70 篇文档、180 道问题。保留有价值的旧语料，补充同产品不同适用条件、相近错误码、操作步骤和例外条款。旧实验问题可作为回归题，但不得混入新独立测试集后声称全部未见。

正式问题分为开发集 60 题、测试集 120 题。其中开发集建议 50 道可回答题、10 道无答案题；测试集 100 道可回答题、20 道无答案题。按 90 个问题家族分组，每个家族两种自然表达；开发集 30 家族、测试集 60 家族。同一事实问题的改写不能跨集。

如果现有真实材料不足，可以使用明确标记的合成政策。不能把合成样本规模当作真实用户覆盖规模。每个家族按政策事实和适用条件划分；同一文档可在两集出现，但同一事实的近义问题不得泄漏。报告说明这是共享知识库上的问题泛化评测，不是未见文档泛化。

文档与问题至少覆盖：

- 精确实体和错误码检索，以及词面不同但含义相同的表达。
- 同产品不同版本、渠道、时效或适用对象，能区分通用规则与特殊规则。
- 必须同时覆盖条件和结论、多项事实或多个操作步骤的问题。
- 否定、例外和容易误套相邻政策的问题。
- 长章节内部的跨句证据，以及答案确实不在库中的问题。

建议至少 16 篇长文的某个自然章节超过最大候选预算 768，部分超过其两倍。依据文档内容先标注事实，再检查边界覆盖；不能根据某个候选排名结果反向写题。测试集应包含约 20 道长章节或跨边界证据问题，标签可以与其他类型重叠，不需要凑齐互斥配额。

所有正式候选的全库块数应明显大于 Top-K，目标至少 50 块；不能用“全库四块、取五块”的数据证明效果。长文题放入同一个带相似干扰文档的库，不单独对答案文档检索。

### 二 标注结构

每条问题至少保存以下信息，沿用现有字段时提供明确映射：

```json
{
  "id": "rag-v2-001",
  "family_id": "device_refund_exception_01",
  "split": "dev",
  "question": "自然语言问题",
  "answerable": true,
  "tags": ["exception", "multi_fact"],
  "evidence_groups": [
    {
      "fact_id": "refund_condition",
      "alternatives": [
        {"source_id": "device_policy", "quote": "来自原文的准确证据", "start": 0, "end": 10}
      ]
    }
  ],
  "required_conditions": ["必须满足的适用条件"],
  "forbidden_claims": ["与原文相反或无依据的关键结论"]
}
```

上例是字段示意，文本和偏移必须替换为真实值。`start/end` 采用原文字符偏移且 end 不含；若生产分块会规范化空白，评测侧保留对应关系。可使用能定位同一证据的等价实现，不必为了偏移扩展生产接口。

一个事实存在等价出处时计为同一证据组，命中任一合理出处即可；不要把同义出处误算成必须同时命中的两个事实。无答案题证据组为空，另存 `absence_reason` 和易混淆来源，不能杜撰正确引用。

验收：所有引用能定位到对应原文；适用条件和例外无矛盾；近义家族不跨集；无答案题经全库检查确实缺失。对合成数据做语义复核，重点确认“通用退款规则”和“特殊设备规则”的优先适用条件。内容含糊时先修正文档规则，再冻结题目。

### 三 意图数据集

枚举当前真实支持的标签；当前报告覆盖 19 个标签。目标每标签 12 题，共 228 题：每标签开发 4 题、测试 8 题，总计 76/152。按场景家族划分，每家族两种表达；每标签两个开发家族、四个测试家族。

重点补充登录与账号、支付与账单、退款与投诉、投诉与人工升级等相邻类别；加入低关键词、口语改写和三路可能意见不一致的输入。不能从测试题反向生成模板。

另设约 20 条含真实歧义或多意图的诊断题。按现有产品路由规则确定主意图或允许标签集合；没有明确规则的题不纳入单标签 macro-F1，单独分析，不擅自改变业务路由政策。

### 四 冻结和防止测试集调参

完成题目、标签和原文校验后写入数据版本与运行清单。先运行开发集，保存 `selection.json`，内容包括选定块长、overlap、主备 RRF 权重、意图阈值、候选选择理由与正式对比名单，再运行测试集。

执行者可以读取测试数据做格式和证据校验，但不能依据测试排名、错误列表或效果改写参数与模板。若测试后发现实现错误或错误标注，保存原运行，说明受影响范围；修正后重跑相关预定对比。若用测试错误定向优化模型或模板，则这些题转为开发材料，新的提升结论需要新的保留集。

## 六 指标和数据记录

### 一 检索质量

检索直接使用原项目 `evaluation/retrieval_metrics.py::query_metrics`，未修改该函数。Recall@5/10为前K条是否命中任一相关source；Precision@3为前3条首次出现的相关source数量除3；MRR@10为首个相关source的倒数排名，nDCG沿用原来源分级及重复来源零增益。所有查询参与总体均值，包括无答案题：相关来源为空时Recall=1、Precision/MRR/nDCG=0。无答案非空率按原定义单列，不能等同回答编造率。

本次仅对已保存真实排名重计分，未重新编码、检索或生成回答，新增embedding/LLM调用均为0。检索逐题保留前10条，实际生产工具返回Top5；相同生产题的离线比较也截断到Top5。原逐事实引用/条件标注仍供数据校验和回答审核使用。

同时报告来源Recall@5/10、来源去重Precision@3、来源MRR@10/nDCG@10、各类型样本与逐题排名、返回上下文长度/块数、Top3重复chunk率及句子级近似重复比例。近似重复比例不等同精确overlap成本。原事实/条件标注保留作回答审核依据，不新增检索评分。

检索非空率沿用原算法对无答案题单列，回答是否编造通过真实模型审核另报；不以非空检索直接判定误答。

### 二 意图质量

报告 macro-F1、accuracy、每标签 precision/recall、混淆矩阵、OTHER 输出比例。重点报告三路相对两路的“改对了多少题、改错了多少题”，附相同 LLM 输出和关键词结果下的逐题对照。不能把 embedding 余弦相似度直接描述为正确概率。

### 三 延迟与成本

区分以下计时，不把复用数据模拟的延迟描述为生产实测：

| 指标 | 记录内容 |
|---|---|
| 导入 | 分块、计数、文档向量化、写索引的耗时及片段总数 |
| 在线检索 | 实际编码、向量召回、BM25、融合和端到端耗时 |
| 意图冷启动 | 模板准备耗时、模板请求量、首次请求体验 |
| 意图热路径 | 模板已准备时，LLM、embedding 和融合耗时 |
| 实验等待 | 配额限速、重试等待单独列出，同时保留用户实际墙钟时间 |
| API 用量 | Google HTTP 次数、计数次数、文档和查询及模板文本编码数、LLM 网关调用数、返回 token 用量 |

报告 P50/P95 时列明样本量。质量实验中跨变体复用向量和 LLM 输出是控制变量手段；延迟比较另以小批固定问题走实际路径。SDK 内部未观测的重试用量明确标记未知，不估造完整账单。

### 四 结果可信度

保存每题检索块、来源、排名、证据命中、错误、计时和配置。相同问题家族的改写不是独立样本；效果差异的区间按 family_id 做配对聚类 bootstrap，可使用 1000 次重采样和固定随机种子。优先复用仓库已有实现。

本轮预先把主指标变化 2 个百分点作为“值得关注”的参考量级，而非强制追求的成绩。是否采用还要看具体退化、适用条件错误、成本和区间。不把指标组合成一个总分，也不把统计区间当作真实用户收益保证。

## 七 阶段三 分块与检索实验

### 一 起点复测

在新开发集上先测当前实现：Gemini 结构递归 512/0，向量、BM25、等权混合；MiniLM 固定 240/0 的向量、BM25、等权混合。关闭查询改写、LLM 重排和回答。单路 Top-K=5，向量和 BM25 的候选上限固定为 20；RRF 的 k 记录仓库实际值并固定。

这组结果用于确认数据是否仍然饱和、检查备用混合退化的原因。若开发集全部饱和，补充有实际业务意义的干扰和复杂条件，然后重新校验冻结开发集。不能先看正式测试表现再选择增加哪类题。

旧 500 字符与 MiniLM 截断结果只保留为历史说明，本轮不重复用它证明 Gemini 的纯语义能力更强。

### 二 Gemini 分块比较

固定 Gemini、768 维、标题规则、向量召回、overlap=0、候选数和 K，只改变分块方式与块长：

| 组别 | 分块方式 | 候选预算 |
|---|---|---|
| C1–C3 | 普通递归 | 256、512、768 |
| C4–C6 | 结构感知递归 | 256、512、768 |

预算均包含现有标题与余量规则，不能一个方案按正文、另一个方案按总输入。主结构方案仍保留章节追溯；普通递归用于消融。不能为了对齐块数人工改写文档。

开发集选择一个结构方案块长，按原Recall@5、Precision@3及成本判断。若差异不明确，保留 512。普通递归结果用于判断结构切分的实际贡献；如果它更好，报告事实，本轮不自动取消已选的结构感知产品方案。

### 三 overlap 比较

固定选定结构方案块长、Gemini 和向量召回，比较 overlap=0、32、64。0 组复用已有结果，因此一般只新增两组。重叠只发生在同一章节内；短章节和独立短问答不应为了满足数值强行复制。

记录请求值和实际重叠分布，因为自然句子边界可能导致实际长度少于设置值。检验所有块仍满足预算，无章节间污染，无事实丢失。

选取规则：

- 正值 overlap 只有在开发集提供清楚的证据收益且未引入重要条件错误时才进入最终候选。
- 若正值降低原Recall或Precision，选择 0。
- 若收益不明确，而重复、片段数、上下文或调用成本增加，选择 0。
- 若正值有收益，选收益相近时更小的一档；在最终混合检索下再与相同块长的 0 组做一次开发集确认。
- 测试集仅检验此前冻结的 0 组和候选。若候选在保留集上退化，生产保留 0，不依据该测试继续搜索新 overlap。

不要求某一固定提升幅度，也不因“行业常用”而启用 overlap。0 是完整有效的实验结论。

### 四 主路径融合

固定开发集选定的主分块，复用完全相同的向量排序和 BM25 排序，比较向量权重 α 为 0.25、0.5、0.75，BM25 权重为 1−α。加权 RRF 公式为：

`score(chunk) = α/(k + vector_rank) + (1−α)/(k + bm25_rank)`

某路没有该块时，该项为 0；不能把不存在的排名当作零名次。纯向量与纯 BM25 分别通过真正的单路路径作参照，不能用权重为 0 但仍执行该路的混合模式冒充单路成本。

优先在现有 `weighted_rrf` 参数上接入配置，不重写融合算法。质量近似时保留等权，不能从相似度和 BM25 原始分数直接加权代替 RRF。

### 五 备用路径融合

MiniLM 分块、模型、tokenizer、标题规则和备用向量不变。比较 α=0.1、0.25、0.5，以及真实单路向量和 BM25。只重算融合结果，不重新生成相同文档向量。

重点解释旧报告中 BM25 1.0、混合 0.7778 的退化：列出正确 BM25 证据在融合前后的排名、被谁挤出、是否相同来源冗余或弱向量干扰。

在开发集选择正权重混合候选。用户已经确定生产使用混合检索，纯 BM25 是对照；如果所有混合仍明显不如 BM25，如实记录产品决策待讨论，不能擅自把生产切为纯 BM25，也不能给混合加“最优”结论。

### 六 正式检索对比

开发集决策冻结后，在测试集只跑预先指定的必要组：

1. 当前主配置 512/0/等权。
2. 选定主候选。
3. 与主候选相同分块的纯向量和纯 BM25。
4. 若选定 overlap 非 0，补相同块长与权重的 overlap=0；若为 0，直接复用。
5. 一个开发集已指定的普通递归对照，用于检验结构贡献。
6. 当前备用等权、选定备用权重、备用纯向量和纯 BM25。

完全相同的组只计算和报告一次。不要在测试集重跑全部网格选择最好的一组。

主候选替换默认值的条件：工程验收通过；测试Recall@5与Precision@3未出现有意义退化；没有新增已核实的关键适用条件错误；收益或成本改善足以解释参数调整。若证据不足，保留当前配置并交付实验结论。备用权重采用同样原则，且与当前备用等权比较。

正式报告可描述观察到的差值；只有预定主指标改善、区间和逐题案例都支持时，才使用“本合成评测集上稳定改善”等限定表述。不能推广为业界普遍最优。

## 八 阶段四 意图 embedding 和模板冷启动

### 一 分类对照

必须比较两路 85/15 与 Gemini 三路 70/20/10。旧字符三路可以保留为历史对照，不接回生产。对每道题只生成一次真实 LLM 分类输出，复用到两组融合，关键词结果也一致；另外记录并行执行的实际耗时。

模板仅来自原模板和开发材料。先固定模板，再比较开发阈值 0.4、0.5、0.6；必要时保留原阈值。不能调整融合权重补偿测试错误。

测试集输出每类结果、改对与改错样本、三路分歧及 OTHER 比例。对真正多意图的诊断集独立解释，不用多个“也合理”的答案随意抬高 macro-F1。

### 二 模板准备优化

目标是避免每次进程重启后的第一个用户请求承担整批模板远端编码。优先实现简单的本地模板向量缓存，并利用现有生命周期做有界准备；不是新建独立缓存服务。

缓存匹配条件必须包含实际模型、维度、`CLASSIFICATION` 任务、模板内容及顺序。直接比较保存的配置和模板即可。匹配时读取；不匹配时重新编码，不能把旧模型向量当作新向量。在线模板学习发生后，当前内存缓存和持久缓存不能继续命中旧模板。

缓存不存在且 Google 暂不可用时，服务可以按已确定的 85/15 路径工作，并记录降级；模板准备不得使所有首次请求无限等待。是否后台准备按现有生命周期决定，避免重复创建不受管理的后台任务。必须覆盖关闭与失败恢复。

验收：

- 同一实例并发首次识别只触发一轮模板构建；其余请求有界等待或按约定降级。
- 重启后模板和配置相同，模板编码调用数为 0；消息编码仍按正常识别发生。
- 修改模板或模型配置时不能复用不匹配的缓存；错误缓存可重新生成且不影响两路兜底。
- Google 分类失败时按 85/15，恢复后按 70/20/10；结果缓存不能锁住降级状态。
- 单独记录冷启动、缓存命中启动和热请求，不把旧报告受实验限速影响的 111 秒当作固定生产收益基线。

分类效果没有超过两路时，本轮仍保留用户选择的三路配置与降级机制，报告其开销和未证明的增益；改变是否启用 embedding 是后续产品决定。模板缓存节省的重复调用可以独立作为工程收益。

## 九 阶段五 回答质量与运行集成

### 一 回答实验

从正式 RAG 测试集预先选定 30 题：建议 24 道可回答题、6 道无答案题，包含条件例外、长文、多事实和精确错误码。名单在查看检索结果前冻结，避免只挑某方案擅长的题。

对比当前主配置、选定主候选、选定备用候选；同配置可复用。固定聊天模型、提示词、温度、候选数、重排输入预算和最终上下文预算。主回答实验关闭查询改写，隔离检索贡献；另以少量问题验证现有生产改写路径正常运行，不把两类结果混为一组。

每组应保存真实检索、真实重排是否成功、送入回答的实际上下文和最终回答。不能用实验脚本手工拼出的答案代替模型回答。重排失败回退单列，不称为重排成功。

评价逐条检查：必需事实、适用条件、例外、是否有原文不支持的关键断言、引用是否支持相应主张；无答案题检查是否承认材料不足、请求必要条件或错误编造。固定候选数之外，还必须固定上下文预算，避免大块方案用更多文字换取未披露的优势。

可以让 LLM 辅助审核，但不得把同模型审核当作人工确认。交付原文、回答、审核与争议项的复核表。执行代理作出的复核标明“代理复核”；只有人实际检查后才写“人工复核”。无需因此停住其他实验工作。

回答验收：关键事实和条件退化均有逐题解释；新增且已核实的严重错误阻止该候选替换默认；无答案编造不因检索命中高而被忽略。全部回答产物与失败结果保留。

### 二 生产组件一致性

离线排序可能使用全量余弦，而生产 Chroma 使用自己的检索过程。两者不能默认等价。用隔离 collection 对冻结配置和至少 20 道固定问题走真实 `KnowledgeBase` 及工具路径，记录候选、原来源Recall/Precision与排名、主备路由和缓存行为。

发现离线与生产差异导致证据丢失时，以生产结果为验收依据并分析原因；不能只交离线更高的分数。无需强制两者在同分情况下返回完全一致顺序。

默认完成本地 Persistent Chroma 和真实 MiniLM 的集成。若仓库现有 HTTP Chroma、Redis 服务可用，再覆盖已有部署路径。不能为了完成表格擅自更改 Docker 或启动整套外部基础设施；未覆盖的部署边界明确列出。

### 三 主备状态和缓存回归

至少覆盖以下完整序列：正常导入 → Google 查询失败 → 备用真实回答 → Google 恢复 → 降级更新/新增 → pending 时继续备用 → 显式补齐 → 主路径检索新内容 → 删除 → 两路均无法检索该来源。

同时覆盖进程重启后 pending 保留、Gemini 分块参数变更不改变 MiniLM 分块、旧在途结果不回填更新后的缓存。针对本轮改锁和预算造成的风险补测试，不增加无关防御框架。

## 十一 调用预算和失败处理

新会话执行 prompt 授权使用已配置的 API 完成本方案，不要求每一步重复确认。运行前先估计片段数、唯一编码文本、计数请求和 LLM 调用；本轮建议采用以下调用量上限，作为保护实验范围的默认值，不是费用估算：

- Google 编码文本总量上限 10000，包括文档、查询和意图模板；批量请求按文本条数计。
- Google HTTP 请求总量上限 20000，包括计数和可观测的失败尝试。
- LLM 网关调用上限 600，优先分类和回答；辅助审核不足时可以省略并改为交付复核材料。

上限不等于目标调用量。预算不足时优先复用分块、向量与相同 LLM 输出，取消重复组与非必要辅助审核，不删除正式测试题、不减少对照而仍声称完成。若必要实验估计仍超出上限，完成不依赖额度的工作，记录剩余需求并向用户申请扩大范围。调用次数上限不能保证货币费用上限；不能虚构当前价格。

实验保留现有配额限速，记录等待。对可恢复的 429 按服务给出的等待信息处理，建议单个失败条目最多两次有界重试；配额长期不足或认证失败时停止重复请求、保存断点。不得切换成 stub 后声称是真实实验。

需要缺失的密钥、可用模型、外部服务或更多额度时，只阻塞依赖它的阶段；继续本地修复、测试、数据标注和结果分析。最终明确区分 measured、failed、blocked 和未开始。

## 十二 最终验收与采用决策

| 验收层 | 必须满足的条件 | 不满足时 |
|---|---|---|
| 工程正确性 | 四类审查问题修复；超时返回真实备用证据；事件循环不被同步锁阻塞；响应不串批；BM25 零 embedding | 修复，不进入完成状态 |
| 一致性 | 主备隔离、pending、补齐、更新删除和缓存回归通过；MiniLM 分块未被主调参改变 | 修复并复测受影响路径 |
| 数据可信度 | 原文证据有效、家族不跨集、测试前冻结参数、长文与干扰充分 | 先修数据，不发布效果结论 |
| 实验完整性 | 必需组有真实结果、逐题记录、配置和失败说明，生产组件验证完成 | 标记部分完成或受阻 |
| 参数采用 | 候选相对当前配置无有意义退化，条件错误未增加，收益或成本改善有依据 | 保留原参数；overlap 无收益则为 0 |
| 分类结论 | 三路和两路公平对比，质量与延迟分开，冷启动实际测量 | 不宣称分类增益 |
| 可复现性 | 命令、数据、模型、运行状态、原始产物和改动记录齐全 | 补齐缺项 |

“实验完成但候选无提升”是合格交付；“未调用真实模型却填写真实指标”不是。合成数据结果仅支持该评测范围，不能声称线上收益。

最终报告至少包含：四项修复及对应验证；实际环境和命令；数据规模与划分；开发集选择记录；正式测试逐组表与区间；主备退化案例；overlap 的保留或关闭理由；意图质量和成本；回答及无答案表现；生产组件验证；失败与未覆盖边界；最终默认参数和是否需要重建主索引。

求职说明提供两段：一段解释问题、设计和故障恢复；一段只引用真实测得的效果与成本。没有效果提升时，可以讲清为什么关闭 overlap、为什么需要备用权重实验、以及如何保证 Google 故障时仍返回完整知识，不编造准确率或性能提升。
